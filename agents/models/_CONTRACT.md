# Azul AI 脚本契约 v1（生成脚本必读）

你要为《花砖物语》观战模拟器写一个 AI 对战脚本。**只写一个文件**，不碰引擎、不碰界面、不碰其他脚本。

---

## 1. 文件位置

```
agents/models/<你的 id>.mjs
```

（路径相对仓库根目录。）

单文件、自包含：**不要 import 任何其它文件**（包括同目录的 `_lib.mjs`）。所有工具函数自己写在这个文件里。

---

## 2. 导出结构

```js
export default {
  id: 'hy4',                 // 与文件名一致，唯一
  name: '二字到六字的名字',    // 观战界面显示
  tag: '专精',                // 固定写 '专精'
  model: 'hy4',              // 你的模型标识（中文名或英文名都行，照抄任务里给你的）
  modes: [2],                // 支持的对战人数，只写你负责的那一个
  strategy: '策略名',         // 4-8 字，例如「颜色垄断」
  description: '一句话说明，30-60 字',

  create(ctx) {              // 每局调用一次，可以在这里存跨步状态
    let turnCount = 0;
    return {
      chooseMove(view, moves) {   // 每步调用；返回 moves 里的一项
        turnCount += 1;
        return moves[0];
      },
    };
  },
};
```

`tag` 一律写 `'专精'`。

---

## 3. `ctx`（整局不变）

| 字段 | 说明 |
|---|---|
| `seat` | 自己的座位号 `0..n-1` |
| `playerCount` | 2 / 3 / 4 |
| `seed` | 本局种子 |
| `rng()` | 返回 `[0,1)`，种子化随机，同 seed 可复现。**只用它，别用 `Math.random`** |
| `log(...)` | 往观战界面写一行日志。别每步都写，会刷屏 |

---

## 4. `view`（每次决策重新给，只读）

```js
{
  mySeat, myTurn,
  phase,          // 'draft'（选砖）| 'tiling'（结算）| 'over'
  round,          // 第几轮，从 1 开始
  turn,           // 轮到谁
  firstSeat,      // 本轮首玩家
  factories,      // [[颜色号…], …]，空盘是 []
  center,         // [颜色号…] 中央区
  centerFirst,    // true 表示起始玩家标记还在中央
  bagCount,       // 袋中砖数
  bagColors,      // [5] 袋中各色数量（可数信息）
  discardCount,
  wallColor,      // [5][5]，wallColor[row][col] 是颜色号
  seats,          // 全部玩家（含自己）
  moves,          // 当前合法行动（轮到自己时非空）
}
```

`seats[i]`：

```js
{
  seat, name, score,
  floor: [颜色号…],        // -1 表示起始玩家标记
  pattern: [{ color, count }, …],   // 5 条图案行，count 是已放砖数
  wall: [[颜色号或 -1] × 5] × 5,    // -1 表示该格还空着
  bonus,                   // 终局奖励，未结算时为 null
}
```

---

## 5. `move`（行动）

```js
{ source: 'factory' | 'center', index, color, line }
```

| 字段 | 说明 |
|---|---|
| `source` | 从工厂圆盘取，还是从中央区取 |
| `index` | 工厂下标；从中央取时固定 `-1` |
| `color` | 颜色号 `0..4`（蓝 黄 红 黑 白） |
| `line` | 图案行 `0..4`；`-1` 表示整批弃到地板区 |

**合法性由引擎保证**：`moves` 里出现的一定合法，不出现的一定非法。你不需要自己判「这行能不能放这个色」，只需要在 `moves` 里挑一个——原样返回其中一项即可。

## 6. 规则要点（决定策略好坏的部分）

- 100 块砖，5 色各 20。工厂数：**2 人 5 个、3 人 7 个、4 人 9 个**，每盘 4 块。
- 一回合：选一个工厂或中央区，取走该处**某色的全部**砖；工厂剩余的砖滑进中央区。
- 取来的砖放进一条图案行（容量 1~5），**放不下的溢出到地板区**。
- 图案行只能放一种颜色，且该色不能已经出现在这一行对应的墙面上。
- 图案行填满后，只有**一块**上墙，其余砖丢回盒子。
- 上墙立刻计分：孤立 1 分；水平连成 h 块记 h 分，垂直连成 v 块记 v 分，十字交叉是 h+v。
- 轮末结算地板：7 格，`-1 -1 -2 -2 -2 -3 -3`。分数不低于 0。
- 从中央区取砖会拿到起始玩家标记，占一格地板并成为下一轮首玩家。
- 有人补满一整行墙（5 块）时，这一轮走完游戏结束。
- 终局奖励：每完整行 **+2**、每完整列 **+7**、每集齐一色 **+10**。

**关键推论（策略必须建立在上面）**：

- 4 人局轮次更短、工厂更多，**终局奖励权重更高**；2 人局砖极稀缺，**断供与地板控制更重要**。
- 一条 5 格图案行攒满只上墙 1 块，是「用 5 块砖换 1 块上墙」；第 1 行是「用 1 块换 1 块」。所以**行越短效率越高，行越长分数潜力越大**。
- 地板前两格各扣 1 分，第 6、7 格各扣 3 分——**吃到第 5 格之后代价陡增**。

## 7. 必须遵守的工程约束

1. 纯 ESM，无外部依赖，Node 22 直接可加载。
2. **不要用 `Math.random`**，用 `ctx.rng()`。
3. 单步决策控制在 **50ms 以内**（硬超时 900ms，超了会被判弃权）。
4. 不要 `console.log`，要输出就用 `ctx.log()`。
5. 所有 `moves` 遍历都要有兜底：万一算不出最优，返回 `moves[0]`。
6. 文件里不要写 `require`、不要用 `import` 引其它文件。

---

## 8. 自检（写完必须跑）

在仓库根目录下：

```bash
node --check agents/models/<id>.mjs
node tools/check-agent.mjs agents/models/<id>.mjs <你负责的人数>
```

`check-agent.mjs` 会真的开一局，让你的脚本坐 0 号位打完，并报告：
- 导出的 `id / modes / model` 是否正确
- 是否出现过非法返回（兜底次数）
- 最终得分与排名

只有两行都通过（`OK` 与 `对局完成`）才算完成。
